## 与原方案的差异(实施时调整)

实施过程中相对最初方案的补充与修订:

1. **多文件聚合(新增需求)**:除原方案的单 PDF 通道外,实际需求是「一次上传多个 PDF、统计所有文件总金额」。实施时把端点改为 `target: list[UploadFile]`,流水线 `run_statement_pipeline(pdf_paths, file_names)` 串行处理所有 PDF 并聚合:
   - 输出 `StatementSummaryReport.grand_total`(所有文件金额总和)
   - `StatementFileSummary` 记录每个 PDF 的统计;单文件失败不阻断其他文件(`error` 字段 + 整体 verdict 标 `needs_review`)
   - 前端新增 `FileDropMulti.vue` 多文件上传组件(原 `FileDrop.vue` 仅单文件,且不修改以免影响其他提交页)
2. **金额抽取复用边界**:原方案第 2 步表述「从 elements 模块 import 复用」 `_ARABIC_AMOUNT_RE` / `_canonical_amount` / `_parse_decimal`。核实后发现这些是 `compare/elements.py` 的**私有**符号。实施改为封装一个公开入口 `statement/amount_column.py::extract_amounts_from_cell`,内部调用 `elements._fact_spans`(已处理金额/日期/比例的重叠优先级,比单条正则更鲁棒),把对私有的依赖收口在一处。
3. **LLM 兜底调用方式**:原方案说复用 `ocr/llm.py::_to_data_url + _post_chat`。`_post_chat` 是 `LLMOCREngine` 的实例方法(依赖 self 配置,带重试+埋点)。实施改为实例化 `LLMOCREngine()` 后调 `engine._post_chat(payload, kind="statement-column")`,`_to_data_url` 直接 import(模块级函数)。
4. **LLM 列定位 → 代码求和**:LLM 返回 `{col_index: role}` 后,pipeline 用 `column_roles_override` 传给 `summarize_table`,强制按 LLM 给的列索引用代码抽金额 + 求和。LLM **绝不**参与数值识别或算术。
5. **测试 mock 模式**:API 冒烟测试中,多文件 multipart 在 `TestClient` 下需要用 `list-of-tuple`(`[('target', (...)), ('target', (...))]`)而非 dict 单键 list 形式;后者会触发 multipart 解析错误。`from document_comparison.api import app` 因 `api/__init__.py` 的 `from .app import app` 会被绑定到 FastAPI 实例,monkeypatch 需直接 `setattr(task_manager, "run_statement", _noop)` 而非通过路径。

## 1. 需求背景

新需求：金额统计。

- 输入：对帐单扫描件 PDF（无文本层，需 OCR）
- 内容：含表格，多行，需统计表格金额
- 难点：对帐单样式可能很多（合并单元格、跨页表格、单页多表）
- 目标（用户确认）：
  - 求和（总计）
  - 核对表格内声明的合计行
  - 按列分类统计（已付/未付/小计等多金额列）
- 列定位策略（用户确认）：**自动启发式 + LLM 兜底（推荐）**
- 表格复杂度（用户确认）：合并单元格 + 跨页表格 + 单页多表
- 输出形式（用户确认）：**JSON 结果（必须）**

## 2. 现有能力盘点（可复用）

| 能力 | 现状 | 文件 |
|---|---|---|
| 多模态 VL-OCR（看图） | ✅ `LLMOCREngine` 支持 `image_url`，Qwen-VL-Max/GPT-4o | `ocr/llm.py` |
| 扫描件双层降级 | ✅ Native 优先，不可靠才走视觉 | `ocr/trusted.py` |
| 表格结构识别 | ✅ `TableStructure(headers, rows)` | `models.py` |
| **金额正则（含中文数字、万元换算、¥ 符号）** | ✅ 已实战检验 | `compare/elements.py` |
| 表格单元格金额定位（行号+列名） | ✅ `extract_table_key_elements` | `compare/elements.py` |
| 独立功能通道模式 | ✅ 可复刻 `raw-compare` 四端点 | `api/app.py` |

## 3. 方案对比

### 方案 A：纯 OCR + 代码统计
扫描件 → VL-OCR 转 `TableStructure` → 代码遍历定位金额列 → 正则提取 → 确定性求和

- ✅ 算账可审计、可重跑、零幻觉
- ✅ 复用 `compare/elements.py` 现成正则
- ❌ 表格样式多变时，"哪一列是金额"靠启发式列名匹配，可能漏列/错列
- ❌ 合并单元格、跨页表格需额外处理

### 方案 B：纯多模态 LLM 直接统计
扫描件 → LLM 直接输出"每行金额 + 合计" JSON

- ✅ 对样式多样性最鲁棒，实现最简
- ❌ **LLM 算账有幻觉风险**（多行数字相加是公认的弱点）
- ❌ 结果不可审计（无法说清 30000 怎么来的）
- ❌ 与 AGENTS.md「LLM 不能撤销确定性结论」理念冲突——金融场景算账必须确定性

### 方案 C（推荐，本方案）：OCR 识别 + 代码统计 + LLM 仅兜底/校验
1. **识别**：复用 VL-OCR 把表格转 `TableStructure`
2. **统计**：复用 `compare/elements.py` 正则提取金额，代码确定性求和
3. **校验**：若表格自带"合计"行，对比"代码求和 vs 声明合计"，不一致标 `needs_review`
4. **兜底**：仅当列名无法启发式识别、或 OCR 表格结构混乱时，才让多模态 LLM 补充"每行金额+列名"——**但仍由代码做最终求和**

这个方案与项目「确定性优先、LLM 辅助」的核心理念完全一致，也是 AGENTS.md 明确的方向。

## 4. 实施计划

> 独立通道（仿 `raw-compare` 模式，与现有合同比对完全解耦）

### 第 1 步：数据结构（`src/document_comparison/models.py`）

新增以下 pydantic 模型（与 `TextDiffReport` 同级独立，不进 `TamperReport`）：

```python
class StatementAmountItem(BaseModel):
    """单行金额明细。"""
    row_index: int          # 在所属表格中的行号(0 基)
    row_label: str          # 该行的标识(首列单元格,如日期/项目/客户名)
    raw_cell: str           # 金额单元格原始文本(OCR 识别结果)
    amount: str             # canonical 形式(如 "CNY:30000.00")
    parsed_value: float     # 解析后的数值(单位元)
    column: str             # 所属列名(启发式匹配或 LLM 指认)

class StatementTableSummary(BaseModel):
    """单张表格的统计结果。"""
    table_index: int        # 表格序号(全文顺序)
    page_index: int         # 起始页(0 基)
    headers: list[str]      # 表头
    column_sums: dict[str, float]  # 按列分别求和(支持"已付/未付/小计"多金额列)
    declared_totals: dict[str, float]  # 表格内"合计/小计"行声明的值(按列)
    totals_match: dict[str, bool]      # column_sums vs declared_totals 是否一致
    items: list[StatementAmountItem]   # 逐行明细(可审计)
    skipped_rows: list[int]            # 被跳过的行号(如合计行本身避免重复计入)
    column_source: dict[str, Literal["heuristic", "llm", "declared"]]  # 列定位方式

class StatementSummaryReport(BaseModel):
    """金额统计报告。"""
    source: str             # 文件名
    target: str
    total_amount: float     # 全文档总合计(所有表格所有金额列之和)
    tables: list[StatementTableSummary]
    grand_totals_by_column: dict[str, float]  # 跨表按列名汇总
    has_declared_grand_total: bool
    declared_grand_total: float | None
    grand_total_match: bool | None   # 总计 vs 声明总计
    verdict: ChangeVerdict  # clean / changed(声明不一致) / needs_review(OCR/列定位低置信)
    reasons: list[str]      # 判定理由(如"合计行声明 1000,实算 1005")
    recognition_status: RecognitionStatus
    recognition_diagnostics: list[PageRecognitionDiagnostic]
    column_detection_summary: dict   # 启发式命中/LLM 兜底/失败统计

class StatementOptions(BaseModel):
    """对帐单统计提交选项。"""
    ocr_backend: Literal["llm", "paddleocr"] | None = None
    amount_column_keywords: list[str] | None = None  # 可选:用户自定义金额列关键词
    enable_llm_column_detection: bool = True          # 启用列定位兜底
```

### 第 3 步：流水线编排（新建 `src/document_comparison/statement_pipeline.py`）

仿 `raw_pipeline.py` 的结构（独立、不共享中间态），签名带 `on_progress`：

```python
def run_statement_pipeline(
    pdf_path, *, cfg=None, ocr=None, on_progress=None,
    ocr_backend=None, amount_column_keywords=None,
    enable_llm_column_detection=True,
) -> StatementSummaryReport:
    # ① 渲染 + OCR:复用 get_ocr_engine(ocr_backend) → TrustedPDFReader
    #    拿到 list[list[Block]](含 label=table + TableStructure)
    # ② 抽取所有 label=table 的 Block.table → [(table, page_index), ...]
    # ③ merge_cross_page_tables 合并跨页续表
    # ④ 对每张表 summarize_table():
    #    - 启发式 detect_amount_columns 命中 → 代码求和
    #    - 启发式失败且 enable_llm_column_detection → 渲染该页 PNG 调
    #      llm_detect_amount_columns 兜底指认列,再代码求和
    #    - LLM 也失败 → 该表标 needs_review
    # ⑤ 汇总 column_sums → grand_totals_by_column;核对 declared_grand_total
    # ⑥ verdict: 任一表 totals_match=False → 'changed';
    #         任一表 LLM 兜底失败或 OCR unreliable → 'needs_review';
    #         否则 'clean'
    # ⑦ 携带 recognition_diagnostics(复用 TrustedPDFReader 的诊断)
```

**与现有 raw_pipeline 关键区别**：
- 不需要 Word 输入（对帐单统计是单端：只读 PDF）
- 不做 LLM 整篇比对，只做表格抽取 + 代码求和
- LLM 调用仅用于列定位兜底，单次调用、范围有限

## 5. 关键设计原则（贯彻全程）

1. **确定性优先**：金额抽取复用 `compare/elements.py` 实战正则；求和用 Python `sum()` + `Decimal`；与 `compare/adjudication.py` 的 `max_risk` 护栏同理念——LLM 只能辅助、不能撤销确定性结论
2. **可审计**：每笔金额带 `row_index + col_header + raw_cell + parsed_value`，能追溯"150000 是哪几行哪几列加出来的"
3. **降级语义**：OCR unreliable / 列定位失败 / 声明不一致 → `needs_review`（与项目 `quality.py` 的 `needs_review` 理念一致），不强行下结论
4. **样式鲁棒**：启发式列名 + LLM 兜底，覆盖多样式对帐单（用户已确认场景含合并单元格/跨页/单页多表）
5. **独立通道**：与 `raw-compare` 同模式，存储文件名 `.statement.json` 隔离，不污染现有合同比对
